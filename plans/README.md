## Findings considered and rejected

- **D1 for the product catalog:** rejected for the first version. The current upstream snapshot is roughly 105,000 offer rows before indexes; D1 Free allows 100,000 rows written per day and index maintenance also counts as writes. The workload is a daily bulk rebuild followed by read-heavy search, so immutable R2 artifacts are cheaper and simpler.
- **Workers Cache API in front of an R2 binding:** rejected for the hosted path. Cache API entries are local to a data center and do not use Tiered Cache. Hosted reads should fetch an R2 custom domain covered by Cache Rules and Smart Tiered Cache; self-hosted/local deployments may use the R2 binding directly.
- **R2 for shopping lists and watches:** rejected. Public catalog data and private capability-held state have different ownership and deletion needs. Small, strongly consistent list state belongs in SQLite-backed Durable Objects and must never be placed in the public catalog bucket.
- **A generic shared storage package now:** rejected. `CONTRIBUTING.md` says source-specific adapters stay inside their owning MCP until two MCPs genuinely share them. Publish a narrow catalog interface and documented artifact format from `mcp-groceries`; extract it only when a second MCP needs it.
- **A server-side birthday-party planner or LLM:** rejected. Hermes/OpenClaw should reason from the user's occasion and call `plan_grocery_basket` with concrete items and quantities. Stamppot's job is deterministic product matching, package arithmetic, price comparison, totals, and explicit uncertainty.
- **Caller-generated IDs or a stored quote object for one-shot basket pricing:** rejected. Ordered input plus returned `lineNumber` is enough to correlate results, and a version-pinned `replayInput` makes refinement deterministic without requiring model memory or allocating state for a read.
- **Treating an MCP connection/chat as shopping-list identity:** rejected. Remote MCP requests are stateless and clients reset or compact conversations differently. Persisted lists use an explicit bearer `listKey`; losing it is unrecoverable in v1.
